# 32. Every dataset query in milliseconds, and a lean lake

## Goal

Every question to every dataset (app routes, `quick` templates, agent tools, MCP, the data API)
answers in milliseconds where physics allows it. The lake should also hold no byte it does not
need.

Brief 30 (PR #19) brought the asks from p50 7.05 s to 2.20 s with the fake model, warm data
routes to 0.01 s, and added H3 rollups, instant answers and a result cache. What is still slow:

- The first instant answer in a fresh process: 4.93 s.
- `resolve_area` p95: 4.0 s.
- Large tables read from R2 Parquet whose row groups are far too big. The England flood
  zones: one row group of about 200 MB per file. Italy's census sections: 252,126 rows per
  group. The lake's own standard (DATA_LAKE section 4) says 32-128 MB.
- Some tables took 5-8.5 minutes to return a single row on a slow line (owner's laptop,
  2026-11-05, eight tables at once).

**Be honest about physics.** A network round trip to R2 costs tens of milliseconds, and a scan
of gigabytes cannot finish in milliseconds. So the design is tiered: answer from memory when
the answer can be prepared; read the fewest bytes possible when it cannot; measure every
dataset and report the ones that miss, with the reason.

## Step 1. Measure every dataset (first commit)

Write `backend/probes/probe_query_speed.py` and a workflow job that runs it in the
Lambda-sized container (2 vCPU, 3,008 MB) against the real lake.

1. Run a standard query set on every lake table and app table:
   - a count;
   - a lookup by id;
   - the rows inside a city (Berlin), a region (Bavaria) and a country (Germany or the
     table's own country);
   - the top 10 by its main measure;
   - a sum by fuel or class where the table has one;
   - and, for tables with geometry, `in_area` and `intersects_area`.
2. Also measure every data route, every `quick` template, `resolve_area` for 50 names at all
   levels, and `area_stats` per measure.
3. Record cold and warm p50 and p95, bytes read from R2, R2 requests and rows returned.
   Write the results to `docs/research/query-speed.md` (the table per dataset) and to
   `data/query_speed.json` (for the CI check of Step 6).

## Step 2. Tier 0: prepared answers (target p50 under 50 ms, served from a cache)

- **Area profiles.** Precompute the answer (the area card's families, with sources and "as
  of") for every area people ask most:
  - every country, NUTS 1-3 region, US state and county;
  - every GB local authority district;
  - every GHS urban centre;
  - every LAU or `localadmin` division with 10,000 people or more.
- **Common queries.** Also precompute the `quick` templates' common combinations: the top N
  per area and kind, totals by fuel and status.
- **Storage and serving.** Store the results as compact JSON in the public bucket, behind
  Cloudflare's cache or a Worker (the Worker exists, `vault/backend/backend-deploy.md`), keyed
  by area id and template. The app and the backend read them before running any query.
- **Freshness.** Rebuild with the datasets' refresh cadence (brief 30, Track 3). Each answer
  carries its build time and its sources' "as of" dates.
- **Size budget.** State it in the PR. Keep it compact: no geometry, only figures and ids.

## Step 3. Tier 1: hot data in memory (target p50 under 20 ms, p95 under 100 ms, warm)

- Build `hot.duckdb`, a native DuckDB file with every table and view the agent and app query
  often, in Actions:
  - all app tables;
  - all rollups (H3 res 3-7 and per admin level);
  - every lake table under a size threshold (decide it from Step 1; start with 50 MB
    compressed);
  - the outline name index;
  - simplified outlines for every set.

  Upload it to R2.
- At cold start the backend downloads `hot.duckdb` once to `/tmp` (Lambda allows 10 GB) and
  attaches it read-only. Queries go to `hot` first; the planner falls back to the lake only
  when a table or detail is not in `hot`. Measure the cold start this adds, and keep it under
  10 s or download in the background with the lake as fallback.
- Indexes in `hot`: ART indexes on id columns and name keys; tables sorted by the columns
  queries filter on; spatial tables with an R-tree (DuckDB spatial) or an H3 column.
- Load `resolve_area`'s name index and the outline boxes in memory at start. Target:
  `resolve_area` p95 under 100 ms for names, under 500 ms with the outline read.

## Step 4. Tier 2: the lake rewritten for selective reads (target p50 under 300 ms, p95 under 1 s for a city or region, warm)

- **Rewrite large files with small row groups.** Rewrite every lake file whose row groups
  break the standard. The England flood zones, Italy's census sections, Overture divisions and
  transport, MaStR, Kohesio and every file found in Step 1 are the first. Target:
  - 10,000-100,000 rows per group and at most 32 MB compressed for geometry tables;
  - about 1,000,000 rows for narrow tables;
  - Hilbert or H3 order, the `bbox` covering column, page indexes and Bloom filters on id
    columns.

  Check that every rewrite has the same row count and the same column checksums as before.
- **Partition the biggest tables** by country or H3 res 3 where most questions ask one place.
  Each file stays 50-250 MB.
- **A simplified geometry companion** (e.g. 10 m and 100 m tolerance) for polygon tables, used
  for maps and large areas. The full geometry stays for exact answers, and every answer says
  which geometry it used.
- **The planner picks the cheapest source that answers exactly:** prepared answer, then rollup,
  then `hot` detail, then lake detail. The trace and the answer name the source.
- **Rasters.**
  - Keep `area_stats` on COG overviews for large areas.
  - Read windows in parallel.
  - Cache the blocks of hot rasters in `/tmp`.

## Step 5. Lean storage (R2 holds 38.6 GB, 2026-11-05 audit)

- **Snapshot retention.** Write the policy in `docs/DATA_LAKE.md`: for snapshot tables, keep
  the newest, one per month, and every snapshot a history table needs. The owner approved
  deleting the MaStR snapshot of 2026-10-13: about 1.3 GB across `units_*`, `locations`,
  `grid_connection_points` and `operators`. Delete it after checking that no view or history
  table reads it. Apply the policy to future snapshots in the builds. Other deletions go to an
  owner question first.
- **Orphans.** About 0.18 GB in `lake/wave9` and `lake/wave10` is read by no view. Delete what
  is a leftover of a rebuild; register what is meant to be read. List each object in the PR.
- **Lossless recompression.** Test ZSTD level 19-22 and LERC with zero error on the largest
  rasters:
  - the Global Wind Atlas, 14.08 GB, float32 at 250 m;
  - the GHSL population tiles, 3.98 GB, float64;
  - the WorldCover and slope shares.

  Apply where the saving is worth it and the values are bit-identical (a checksum check per
  file).
- **Lossy options are an owner question, never applied in this run.** Wind rounded to 0.01
  m/s as int16; population as float32. Measure the saving on samples, show the largest value
  change and the change in a few area sums, then write the owner question with a
  recommendation.
- **Agent cache.** Cap its size and expire old entries.
- **Report.** Bucket sizes before and after, and the monthly cost at $0.015 per GB above the
  free 10 GB.

## Step 6. Keep it fast

- A CI check runs the speed probe on a fixed sample of datasets in the backend workflow. It
  fails when p95 grows by more than 20 % against `data/query_speed.json`.
- The lake writer (`scripts/lake.py` and the wave builders) enforces the row group,
  sort and page-index standard, so new files cannot regress.
- `docs/DATA_LAKE.md`, `docs/AGENT.md` (the tiers and the planner) and the vault note for each
  tier are updated.

## Out of scope

- Changing values: lossy compression waits for the owner.
- Model work.
- Moving the hosting (Lambda or Cloudflare): measure, and write an owner question if the
  numbers favour a move.
- Deleting anything beyond the approved snapshot and verified orphans.
