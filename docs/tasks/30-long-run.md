# 30. The long run: data, coverage, agent speed, design and new product features

## Goal

The owner is away for several days. This brief is a long, self-directed run with seven
tracks:

1. Harden what exists.
2. Fill data gaps.
3. Add new data.
4. Make the backend and the agent's tools faster and better, with instant answers that need
   no model.
5. Polish the frontend.
6. Build new product features end to end.
7. Keep the docs and vault current.

Work through the tracks in order. Inside a track, take the items with the most customer value
first. When an item is blocked, record it and move to the next one; never wait. The owner
reviews everything at the end.

## How to work (a run of days)

- **Token budget.**
  - Chat in `.claude/skills/caveman` (level full).
  - Read vault first, then only the files a step needs (`.claude/skills/atlas-vault`); never
    re-read an unchanged file.
  - Write vault notes with `.claude/skills/obsidian-markdown`.
  - Keep probe output short in chat; full output goes to the PR and `docs/research/`.
  - Use subagents for wide research sweeps when available, so the main context stays small.
- **One branch, one pull request, many small commits.**
  - Open the PR as a draft early.
  - Keep its description as a running changelog with one section per track: done, blocked,
    owner questions.
  - Merge `origin/main` into the branch at least daily, keeping both sides.
  - Before each push: `uv run ruff check . && uv run ruff format .`, `uv run pytest`,
    `cd backend && uv run pytest`, `cd frontend && npm run build`.
  - Never push `main`. Never commit to `eu-data` or `eu-days`, and never force-push them.
- **Checkpoints.** At the end of each track, append to `vault/log.md`, update the notes it
  changed, and update the PR description. A future session can then resume from the vault
  alone.
- **Owner questions** go to `docs/owner-questions.md`: the decision, the options, a
  recommendation and the evidence. Then continue with something else.
- **Budgets.**
  - The repository is public, so Actions minutes are free; still, one heavy job per category,
    not per source.
  - R2 holds 38.2 GB today (2026-11-04). Do not add more than 20 GB without an owner
    question first. The 10 GB free tier is already exceeded, and storage costs
    $0.015/GB-month.
  - No paid services, no new accounts, no billing.
- **Rules that never bend** (CLAUDE.md, briefs 26-28):
  - Every number is sourced: passthrough or computed with the method stated. Never estimate;
    no composite scores.
  - Never hide records to make a map clearer.
  - No non-commercial or login-only sources. Never bypass a refusal (403, 451, robots.txt,
    terms, logins, deliberate encoding); respect CEII.
  - Keys stay in the environment.
  - Commits carry no AI attribution.
  - **No Claude Code session link** in PRs, commits or files. If your environment appends a
    "Generated by Claude Code" footer with a session URL to the PR description, delete that
    line before you finish.
- **Visual rules.** Calm, reference-clean maps; the grid stays the hero. One Layers panel and
  one context panel; no new floating panels. Keys stay compact and off the land. Animation only
  where it carries data. The owner has design changes of their own coming, so keep changes
  incremental and consistent with the current look; no redesigns.

## Track 4. Agent and backend: faster, cheaper, better

This track is about everything except the language model: the data layer, the tools, the
API, the agent's plumbing and the answers it can give without a model.

Measure first. Write `backend/probes/probe_latency.py`. It runs the 30 most common eval
questions with the fake model, plus every data route, and records for each:

- time to first event;
- time per tool call: SQL, `resolve_area`, `area_stats`, map building;
- lake read time and bytes read;
- SSE overhead.

Run it from the Lambda-sized container in Actions (2 vCPU, 3,008 MB) and put the
before/after table in the PR.

1. **Backend latency targets** (with the fake model, so only our own code is measured):
   - tools: p50 under 2 s, p95 under 5 s for a city or region;
   - a cold start under 10 s to the first event;
   - data routes: p50 under 1 s.

   Ways to get there:
   - Warm the lake on start: attaching `lake.duckdb` took 65 s on a slow line. Cache its
     catalogue locally and reuse the connection.
   - Turn on DuckDB's HTTP metadata cache and the httpfs cache.
   - Pre-aggregate rollups per level (NUTS 3, county, LAU, H3 res 5-7) for the large tables
     (MaStR, Overture power, GRW, the big wave 9 tables). Then `in_area` sums read rollups for
     large areas and rows only for small ones; the answer says which.
   - Run independent tool calls in parallel.
   - Cut the Lambda image size and import time (lazy imports, fewer packages).
2. **Instant answers without a model** (new: fast, free and grounded by construction). Use SQL
   templates for the questions most people ask:
   - an area's profile (the area card's families);
   - the top N assets of a kind in an area;
   - totals by fuel or status;
   - two areas compared;
   - what is published here.

   Serve them as `GET /api/quick/{template}?area=…` in under 1 s, each figure with its
   source, method and "as of" date. Wire them in two places:
   - **The app:** the area card and the Ask chat show the instant answer at once, and the
     agent is only needed for open questions.
   - **The agent:** a `quick` tool, so it reuses the templates instead of writing SQL.

   A router rule sends a question that matches a template straight to it, with no model call.
   Evals check that the template numbers equal the SQL ones.
3. **Result cache.** Cache tool results keyed by the normalised SQL or the tool arguments
   plus the lake catalogue date, locally and in R2 (`agent/cache/`, with a size cap and an
   expiry). Repeated questions and map edits then read the cache; the trace says "cached".
   Invalidate an entry when the lake catalogue date changes.
4. **Robust streaming.**
   - SSE resume after a dropped connection (`Last-Event-ID`) and a cancel route.
   - A timeout per tool; on timeout, a partial answer that says what is missing.
   - Load test with the fake model: 50 concurrent asks plus the data routes, with p95 and
     errors reported in the PR.
5. **Security tests.**
   - Prompt-injection cases: data rows and tool results containing instructions must never
     change the agent's behaviour. Add evals.
   - Fuzz the SQL guard (functions, paths, comments, unicode).
   - Rate limits per IP and per key, input size caps.
   - Check that no route leaks a key or a stack trace.
6. **New agent tools** (each with tests, catalogue use and an eval):
   - `nearest(point or area, dataset, k)`: assets nearest a point, with distance (computed).
   - `along(line or route, buffer_km, dataset)`: assets along a corridor.
   - `compare_areas(areas, measures)`: the same measures for 2-6 areas, in one result.
   - `trend(area, measure, years)`: a time series for an area from the history tables.
   - `export(result_id, format)`: CSV, GeoJSON or Parquet of a result with its sources and
     licence. Refuse share-alike or no-redistribution sources, or apply their terms.
   - `explain_coverage(area, family)`: what is published there and why a cell is dark.
7. **Answer plumbing** (model-independent):
   - Tool results carry "as of" dates and the area's coverage notes, so every answer can cite
     them.
   - Follow-up suggestions come from the data the area actually has, computed by the backend,
     not the model.
   - The grounding check covers dates and percentages too.
8. **MCP server:** document it for external agents (`docs/MCP.md`), add the new tools, and
   add a usage example.

   - "Ask about this area" from the area card. Follow-up chips.
   - A permalink per answer (conversation and maps) and export of an answer's data (Track 4

   - Errors say what to try.
3. **Area card.** One card, the same families for every place (the consistency rule). It
   shows what is published, coverage reasons for dark cells, "as of" dates, and a
   compare-with-another-area button that opens the Maps view side by side.
4. **Mobile.** Panels as bottom sheets, the Ask chat full-screen, touch drawing of areas.
   Check at 375 px and 768 px widths with no horizontal scroll.
5. **Accessibility.** Keyboard reaches every control, focus is visible, contrast meets WCAG AA
   for text, colour-blind-safe ramps (check the agent ramps and categorical palette), and
   ARIA labels on map controls.
6. **Freshness and trust.** An "as of" badge on every layer card and colouring, and a coverage
   explorer page (`?coverage`): the registry as an interactive matrix with each cell's
   evidence.

## Track 6. New product features (build MVPs; the owner decides pricing later)

Build each one end to end, behind a feature flag where it is not ready for everyone. Write a
short spec first in `docs/product/<name>.md`: the problem, who it serves, what it shows, its
data and its limits.

1. **Site report.** Pick a point or area and a task (data centre, battery, solar/wind,
   offshore, industrial). The result is a printable HTML report and a PDF export. It follows
   the task skill's checklist, in order, each criterion with its value, source, "as of" date
   and coverage note. No score.
2. **Watchlists and change feeds.** Save an area (in the URL and localStorage; no accounts).
   A scheduled workflow computes what changed per area since the last snapshot: new queue
   entries, capacity changes, new plants, outages, price records. Publish the changes as a JSON
   and RSS feed per saved-area hash, and show a "since your last visit" card.
3. **Compare.** Two to six countries or areas side by side, with the same families and the
   same keys, as maps and a table. The URL is shareable.
4. **Embeds.** An iframe-able view of any dashboard, Maps view or agent map
   (`?embed=1`: no panels, a compact key, the source line), with an embed-code button.
5. **Weekly brief.** A scheduled workflow builds a weekly summary of what changed: biggest
   price moves, new queue entries, capacity added, outages, records. It is written from
   templates over the change feeds and the instant answers, with no language model, and
   published as a page. Every number is linked to its source and "as of" date.
6. **Data API.** The backend's read-only data routes documented with OpenAPI, plus API keys
   and rate limits (no billing). Serve only datasets whose licence allows redistribution, each
   response with licence and attribution.
7. **Download centre.** Per dataset: the file or the lake extract, its licence, attribution
   text and "as of" date. Only redistributable licences.
